# 审查副本导出：实现与验证

本轮落地的是材料选择和导出边界，不宣称外部 Agent 已受权限限制。

## 已实现

- 工作台在审查阶段提供“准备审查副本”。
- 可选择文件或目录，勾选内容，查看排除原因，确认交付版本。
- 后端纯文本打包，不根据 repo 或输入路径读取本地文件。
- 客户端与服务端共同筛选 data/、隐藏目录、常见凭证文件名、依赖和历史试用目录。
- 服务端拒绝路径跳转、重复路径、过大文件和无效文本。
- 副本带完整文件清单、每份 UTF-8 文本的 SHA256、任务内容、执行端差异或引用、验证说明和返回格式。
- 导出不发送第三方，不改变任务状态，不持久保存上传源码。

## 验证

- 语法检查通过，21 项测试通过。
- 浏览器选择真实项目目录，列出 14 个可选文本、32 个排除项；排除了 data/projects.json、隐藏文件、图片与 trials/。
- 取消 PRD 与 README 后生成并下载 12 文件、约 86 KB 的审查副本。
- 下载文件清单中所有 SHA256 与对应本地源码一致，无运行数据路径作为文件条目，无其他演示项目记录。见 export-verification.json。
- 审查状态保持待开始，未再次发送给 WorkBuddy。

## 尚未解决

- 本机命令沙箱探针在当前环境未正常启动，观察到退出码 71 / 134；没有启用无约束命令执行作为回退。
- 外部桌面 Agent 仍可能拥有原来的文件权限。单个自包含副本减少交付材料范围，但不能强制防止其越界。
- 文件名规则不是敏感内容识别器；用户必须预览实际内容。
- 源码与执行端交付版本的对应关系依赖用户确认；SHA256 校验的是本副本实际文本。
- 单文件选择只保留文件名；要保留完整相对目录应选择项目目录。
- 本轮功能尚未经过新的外部独立代码审查，不能沿用上轮 UTF-8 修复的 WorkBuddy 通过结论。

后续自动接入的前置条件仍是实际受控环境或可强制的目录权限。不得仅用提示词白名单宣称安全隔离。


## 追加完成：容器内命令隔离

macOS 探针失败后，检查了已有 Docker 本机服务，并拉取官方 Node 22 Alpine 镜像，固定其内容摘要。新增 review-snapshot.mjs 与 scripts/isolated-check.mjs：严格解析 Markdown 源码快照，核对全部文件摘要后生成临时目录，只读挂载到无外网、非 root、禁提权、有资源限制的容器。不能使用远程 Docker，不挂载宿主项目或 Docker socket，失败不回退到宿主执行。

边界探针实际通过：副本可读、修改副本被拒、写根目录被拒、宿主数据不可读、Docker socket 不存在、外网不可达。副本内语法检查与 21 项测试通过，见 container-check.log。最新宿主代码包含新增解析器测试，共 24 项通过，见 final-test.log。

因此“尚未解决”中的 macOS 探针失败仍属实，但命令执行现已有实际验证的容器路径；WorkBuddy 桌面进程的独立访问权限仍不在此检查器控制内。不要将命令隔离扩大表述为整个外部 Agent 已被隔离。

工作台已登记需求 v2 与新的实现版本，包含实际 v1→v2 diff。v1 的界面导出副本原样保留，没有将历史副本伪装成最新代码。
